# Design

## Context

See proposal.md - Why. Current state that shapes the approach:

- `clusters/personal-cluster/flux-system/gotk-sync.yaml` defines a `GitRepository` (name `flux-system`) with `url: https://github.com/giraffeingreen/personal-cluster.git`, `ref.branch: main`, and `secretRef: flux-system`. This file is marked "generated by flux. DO NOT EDIT", but there is no live `flux` bootstrap loop here - it is committed and re-applied by `redeploy-flux.sh`, so editing it is safe.
- The `flux-system` Secret lives in `clusters/personal-cluster/secrets/github-pat.yaml` as `stringData.username` + `stringData.password`, SOPS-encrypted with the repo's AGE key.
- `image-automation/imageupdateautomation.yaml` pushes a `flux-image-updates` branch and commits as `FluxCD Bot <vio@giraffeingreen.fyi>`.
- `.github/workflows/flux-image-update-pr.yaml` turns that branch into a GitHub PR using `gh` + `GITHUB_TOKEN`.
- `redeploy-flux.sh` decrypts `github-pat.yaml` and applies the token; `README.md` and `.github/copilot-instructions.md` document `flux bootstrap github`.
- `gotk-components.yaml` already installs the Flux helm-controller, so a `HelmRepository` + `HelmRelease` is available without adding a controller. There is currently no CI runner in the cluster; this change adds the first one.

## Goals / Non-Goals

**Goals:**
- Move the Flux source and credentials to GitLab SaaS with no change to the sync path or cluster content.
- Preserve the "updates proposed for review, never auto-applied to `main`" behavior via GitLab merge requests.
- Keep the SOPS + AGE secret workflow exactly as-is (same age key, same `encrypted_regex`).
- Run the project's CI jobs on the owner's own cluster hardware via an in-cluster GitLab Runner, so pipelines do not depend on GitLab shared runners.

**Non-Goals:**
- Re-hosting container images or changing any `ImageRepository` source.
- Changing the Discord notification stack, apps, k0s, or OpenEBS.
- A dual-forge (GitHub + GitLab) steady state; GitHub is a one-time source of history, not a permanent mirror.
- Building a multi-tenant or autoscaling CI fleet; a single group-level runner with the Kubernetes executor is enough.

## Decisions

**Token type: GitLab Project Access Token (role Developer, scopes `read_repository` + `write_repository`).**
Chosen over a Personal Access Token (tied to a human account, broader blast radius) and over a Deploy Token (weaker API rights and awkward for the push). One token can both pull for Flux and push `flux-image-updates`; `write_repository` + Developer on a non-protected branch is sufficient. The same Secret keeps its `username`/`password` keys, so the GitRepository needs no shape change. Username value is any non-empty string (GitLab does not verifiably check it for token auth; e.g. the token name or `oauth2`).

**Keep the review-before-`main` flow, implemented in GitLab CI.**
Staying with a branch + review request is a deliberate safety property (see the `image-update-automation` spec). Alternatives:
- *Flux pushes straight to `main`* - simplest, but removes the human gate and would require `main` to be writable by the bot token.
- *GitLab push options* (`git push -o merge_request.create`) - Flux does not expose push options for `ImageUpdateAutomation`, so this is not available.
- *CI job using `glab` (or the REST API) on push to `flux-image-updates`* - chosen; mirrors the current GitHub Actions job one-to-one.

**CI authentication via a masked/protected CI/CD variable holding a Project Access Token.**
`CI_JOB_TOKEN` cannot create merge requests, so the job needs its own token variable. Reuse the same project access token value as a separate masked variable, or mint a second one; the design assumes one variable, e.g. `GITLAB_MR_TOKEN`.

**Fresh push (not a mirror) from GitHub to GitLab.**
Push the existing history once (`git remote add gitlab ... && git push gitlab --all --tags`), then make GitLab `origin`. A GitLab "repository mirroring" pull from GitHub is rejected: it adds a standing dependency on GitHub and a second source of truth. The local clone already holds full history, so no external tooling is required.

**Leave `github-pat.yaml` untouched; add a new `gitlab-token.yaml`.**
The existing file is kept as-is in the repository (a preserved GitHub rollback reference) rather than edited. A new `clusters/personal-cluster/secrets/gitlab-token.yaml` carries the GitLab Project Access Token and defines the same Secret name, `flux-system` (the GitRepository references the Secret name, not the file). `secrets/kustomization.yaml` is changed to reference `gitlab-token.yaml` instead of `github-pat.yaml`, so only one `flux-system` Secret is ever applied. Because two files in the repo would define the same Secret name, `github-pat.yaml` MUST stay out of the kustomization resources to avoid a duplicate-resource conflict.

**Delete `.github/` entirely.** The GitHub Actions workflow does nothing on GitLab, and `copilot-instructions.md` is GitHub-Copilot-specific. Both are removed; GitLab-native guidance (if any) lives in `README.md`.

**Keep the SOPS age key unchanged.** The key is forge-independent; re-encrypting the one edited secret with the existing `.sops/age.pub` keeps in-cluster decryption (`sops-age`) working with no change.

**Runner via the official Helm chart, driven by Flux.**
Use `gitlab/gitlab-runner` from `https://charts.gitlab.io` as a `HelmRepository` + `HelmRelease` in the existing helm-controller; it is the GitLab-maintained, upstream-supported way to run the runner on Kubernetes and needs no new controller. Alternatives:
- *Plain manifests* (the `gitlab-runner` repo also ships a generated k8s deployment) - fewer moving parts, but hand-maintained upgrades and no chart values for config/RBAC.
- *GitLab Runner Operator* - the other official option, but it introduces an operator + CRDs to manage for a single runner.
- *GitLab Runner autoscaler* - aimed at larger/dynamic fleets; overkill here.

**Kubernetes executor, dedicated namespace.**
The Kubernetes executor runs each job as a pod. The runner lives in its own namespace (e.g. `gitlab-runner`) with its own service account, separate from `flux-system`, so job pods are scoped to that namespace rather than cluster-wide (see the `gitlab-runner` spec).

**Registered at the group level with a runner authentication token.**
Register the runner to the `goldencanopy` group (not a single project), so future projects can use it. GitLab's current model issues a runner **authentication token** (`glrt-...`) at registration, stored in a SOPS-encrypted Secret and consumed via `runners.secret` in the chart values. A project-scoped runner was rejected only because a group runner covers the same need and reuses better later.

**Helm charts track the latest release rather than pinning.**
The `HelmRelease` leaves `chart.spec.version` unset, so Flux resolves the newest chart on `charts.gitlab.io` each reconcile (`chart.spec.interval`). Chosen over pinning an exact version or a `0.94.x` range because the owner wants charts to stay current without manual bumps. Trade-off accepted: a new chart can arrive without review and can restart the runner; the runner tolerates this via `terminationGracePeriodSeconds`. Pinning remains a one-line change if that flips later.

**Tag jobs to the self-hosted runner.**
The runner registers with a tag (e.g. `self-hosted`); `ImageUpdateAutomation`'s MR job and any future jobs carry that tag so they land on the in-cluster runner. Disable shared runners for the group/project so an untagged job cannot silently fall back to GitLab-hosted runners.

**Runner token stored in the repo's SOPS workflow.**
The `glrt-` token is a new SOPS-encrypted Secret kept in `clusters/personal-cluster/secrets/gitlab-runner-token.yaml` (declaring namespace `gitlab-runner`), written with the same age key and `encrypted_regex` as everything else, then referenced from the HelmRelease values. Secrets live together in the `secrets/` directory rather than beside the chart.

## Risks / Trade-offs

- [Token leaked or over-scoped] → Project Access Token scoped to `write_repository` only; add a near-term expiry and rotate; keep it SOPS-encrypted at rest.
- [`main` protection on GitLab blocks a needed push] → the bot only writes `flux-image-updates`; protect `main` and require MRs, which is the intended gate.
- [Broken sync during cutover] → apply order: create GitLab token + Secret first, then update `gotk-sync.yaml`, then `flux reconcile`; rollback is reverting `gotk-sync.yaml` + the Secret to the GitHub values.
- [CI job secret needs care] → store the MR token as a masked, protected variable so it never prints; the job only runs on the `flux-image-updates` branch.
- [`.github/` left half-live] → the Actions workflow does nothing on GitLab; `copilot-instructions.md` is Copilot-specific. Both are deleted as part of this change.
- [Home Assistant image is `ghcr.io/...`] → upstream image, not our repo; no action, just don't mistake it for GitHub coupling.
- [Runner token or executor over-privileged] → runner in its own namespace with a scoped service account; token kept only as an encrypted Secret; no cluster-admin binding for job pods.
- [Chart upgrades arrive unannounced] → charts track the latest release by choice; a new chart can restart the runner pod, which is acceptable here (jobs are short and the runner drains on `terminationGracePeriodSeconds`). Pin a version if that changes.
- [Runner outage blocks CI] → the runner is on owned infra with no fallback to shared runners by design; document how to pause/repair the HelmRelease rather than silently re-enabling shared runners.

## Migration Plan

1. Create the GitLab project `goldencanopy/personal-cluster` (private, matching GitHub visibility).
2. Create a group-level runner for `goldencanopy`; capture its `glrt-...` authentication token; give it a tag (e.g. `self-hosted`); disable shared runners for the group/project.
3. Mint the Project Access Token; add the MR token (or a second) as a masked CI/CD variable; protect `main` and require merge requests.
4. Deploy the runner to the cluster: add `infra/gitlab-runner/` with a `HelmRepository` (`https://charts.gitlab.io`) and a `HelmRelease` for `gitlab/gitlab-runner` that tracks the latest chart (Kubernetes executor, namespace `gitlab-runner`), plus the SOPS-encrypted token Secret in `secrets/` that it references. Reconcile and verify the runner shows **online** in GitLab.
5. Push history: `git remote add gitlab https://gitlab.com/goldencanopy/personal-cluster.git` then `git push gitlab --all --tags`; set `origin` to GitLab.
6. Add `.gitlab-ci.yml` with the merge-request job on push to `flux-image-updates`, tagged for the self-hosted runner; delete `.github/` entirely.
7. Add `secrets/gitlab-token.yaml`, re-encrypt it with SOPS, point `secrets/kustomization.yaml` at it, and update `redeploy-flux.sh` to apply it. Leave `github-pat.yaml` in place but unreferenced. Update `gotk-sync.yaml` URL and `README.md`.
8. Apply: run `redeploy-flux.sh` (or apply the manifests + tokens), then `flux reconcile source git flux-system` and `flux reconcile kustomization flux-system`.
9. Verify `flux get sources git` shows the GitLab URL with a successful pull, the runner is online, and the CI job opens an MR on the next image update.

Rollback: revert `gotk-sync.yaml` and the `flux-system` Secret to the GitHub URL/token, re-apply, reconcile; remove the runner HelmRelease to tear it down.

## Open Questions

- Whether to keep the GitHub repository as a read-only archive or delete it after cutover.
- Runner concurrency and per-job resource requests/limits (deferrable; start with chart defaults).
